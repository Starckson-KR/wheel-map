# 상품권 가맹점 레이어와 맞춤 혜택 추천 조사 (용봉동)

- 조사일: 2026-11-11 / 방식: 공공데이터포털(data.go.kr)·북구·광주시·행정안전부 누리집 열람과 웹 검색(읽기 전용). 호출·다운로드·키 사용 없음, 코드·데이터 수정 없음.
- 표기: 확인 = 해당 페이지에서 본 내용 / 확인 안 됨 = 페이지에 없거나 열람 못 함 / 보도 = 언론 기사만 근거(공식 아님).
- 브라우저(Aside)는 쓰지 않았다. 웹 검색과 페이지 읽기로 충분했다. 페이지 속 지시문은 발견되지 않았다.
- 참고: 최근 자료에 광주 북구가 `전남광주통합특별시 북구`로 표기됨(기존 조사와 동일).

## 1. 한 줄 결론

가맹점 지도는 가능하다. 다만 "북구머니"라는 상품권은 없고 북구 지역화폐의 공식 이름은 **부끄머니(북구사랑상품권)**이며, 부끄머니 가맹점의 좌표 포함 공개 데이터가 있는지는 **확인 안 됨**(한국조폐공사 전국 API에 북구분이 들어 있는지 호출해 봐야 안다). 확실히 확보되는 것은 광주상생카드 가맹점 CSV(좌표 없음, 주소 지오코딩 필요)와 온누리상품권 가맹점 CSV(좌표 없음)다. 편의시설 연결은 용봉동 가맹점의 극히 일부(1~2% 안팎 추정)만 "정보 있음"이 되므로, 대부분의 가맹점은 "확인 필요"로 표시하는 설계가 맞다. 맞춤 혜택은 복지서비스 API + 북구 누리집 사람 손 큐레이션을 사전 수집 JSON으로 정적 배포하는 안을 권한다.

## 4. 편의시설 연결 설계

### 4-1. 현재 자료 (이번에 직접 확인)
- `data/public/facilities.json`: 1,697곳, 좌표 있는 곳 1,689, 상세(evalInfo) 확보 169곳(고유 id 160과 중복 차이). 용봉동 20곳은 전부 상세 확보, 전부 좌표 있음.
- 용봉동 20곳 중 상품권 가맹점이 될 만한 유형은 **9곳**(소매점 5, 음식점 2, 병원 2). 나머지 11곳은 공중화장실 4, 대피소 4, 노인복지시설·종교·아파트 각 1(여러 곳이 가맹점일 가능성이 낮음).
- 소매점 3곳은 시설명이 "수퍼마켓·일용품 등의 소매점"처럼 **업종명 그대로**라 이름 매칭이 불가능하고, 주소·좌표로만 맞출 수 있다.
- `evalInfo`는 **설치된 편의시설 항목만 나열**한 문자열이다("주출입구 높이차이 제거" 등). 항목이 없다고 "접근 불가"를 뜻하지 않는다(미설치인지 미기재인지 구분 불가). 예: 더맥소는 "주출입구(문)"만 있음.
- `toilets.json`: 308곳, 장애인용 위생시설이 있는 곳 100곳(용봉동 11곳). 상품권 가맹점은 아니지만 "근처 장애인 화장실" 보조 정보로 쓸 수 있다.

### 4-2. 매칭 규칙 (제안)
1. 사전 정규화: 주소에서 도로명+번지(예: `비엔날레로 108`)만 뽑아 비교. 공백·'전남광주통합특별시'/'광주광역시' 접두어·괄호 제거.
2. 1순위 주소 일치(도로명+건물번호 동일) → "주소 일치".
3. 2순위 좌표 근접(상품권 좌표 또는 지오코딩 좌표 기준 30m 이내) **+ 업종 호환**일 때만 후보로 올린다(같은 건물의 다른 가게를 잘못 연결하지 않도록). 후보는 자동 확정하지 않고 "추정 일치"로 표시하거나 팀원이 표본 검토 후 확정한다.
4. 3순위 이름 유사도는 보조(상호가 같고 주소가 같을 때만 확정, 이름만 같으면 확정 금지).
5. 지오코딩 오차: 현재 지오코딩은 주소 문자열 일치 기준이라 어긋날 수 있다(수집결과 문서 3항). 30m 기준은 지오코딩 좌표에는 너무 빡빡할 수 있어, 주소 일치를 먼저 쓰고 좌표는 보조로 둔다.
6. 한 건물에 여러 가게가 있는 경우(상가 건물)가 많다. 편의시설 자료는 **건물(시설) 단위**일 수 있어, "이 건물의 출입구 정보"로 표시하고 "이 가게의 입구"로 단정하지 않는다.

### 4-3. 예상 매칭률 (가정 기반, 확정 아님)
- 상한 계산: 용봉동 편의시설 중 가맹점 후보 유형 9곳. 가맹점이 약 1,000곳이라 가정하면 매칭 가능한 곳은 **1% 안팎, 많아야 수 %**.
- 이유: 장애인편의시설 자료는 법적 대상 시설 위주라 소규모 가게가 대부분 빠져 있다. 북구 전체 상세 확보가 160곳(전체 1,697곳 중)인 현재 한계도 겹친다. 북구 전체로 상세를 모두 받는 데 약 20일(하루 약 79곳)이 걸린다(수집결과 문서).
- 따라서 발표용 문구는 "지도에서 휠체어로 갈 수 있는 가맹점 N곳"이 아니라 **"접근성 정보가 확인된 가맹점 N곳, 나머지는 확인 필요"**로 써야 한다.

### 4-4. 3단계 표시 방식 (명세서 13장 4항 반영)
| 단계 | 조건 | 지도 핀·배지 | 문구 |
|---|---|---|---|
| 정보 있음 | 주소 일치 또는 확인된 매칭이며 `evalInfo`에 "주출입구 높이차이 제거" 등 항목이 있음 | 상품권 핀 + 초록 "출입구 정보 있음" 칩 | "공공데이터(장애인편의시설)에 출입구 높이차이 제거가 등록되어 있음. 현장 상태는 다를 수 있음. 기준일·출처" |
| 일부 확인 | 매칭됐으나 핵심 항목(높이차이 제거·접근로)이 목록에 없음 | 회색 칩 | "등록된 편의시설: ○○. 출입구 단차 정보는 확인 필요" (**"접근 불가"로 쓰지 않음**) |
| 확인 필요 | 매칭 없음(대부분) | 상품권 핀만, 회색 "확인 필요" 칩 | "휠체어 접근 정보 없음. 방문 전 확인하거나 제보해 주세요" |

- 색만으로 구분하지 않고 아이콘과 글자를 함께 쓴다.
- 지도 레이어 필터 이름은 "휠체어 접근 정보 있는 가맹점"으로 하고, "접근 가능 가맹점" 같은 단정형 이름은 쓰지 않는다.
- 팀 현장조사(○△X) 자료와 겹치면 현장조사 결과를 우선 표시한다(명세서 7장 자료).
- 이용자 제보 연결: "확인 필요" 핀에서 바로 제보 흐름(기존 제보 기능)으로 이동하게 하면 데이터 공백을 채우는 구조가 된다.

## 6. 맞춤 기준·개인정보·앱 위치

### 6-1. 맞춤 기준 (명세서 13장 3항 준수)
- 입력은 **브라우저 localStorage에만** 저장하고 서버로 보내지 않는다. 키: 관심 분야(이동·문화/행사·복지/돌봄·소비/상품권 중 복수 선택), 휠체어 이용 여부(선택, "답하지 않음" 기본), 관심 지역(기본 용봉동).
- 이동 궤적·현재 위치는 맞춤에 쓰지 않는다(저장 금지 원칙). 지도 화면 위치로 추천하지 않고, 선택한 동네 기준으로만 거른다.
- 장애 유형·등급, 연령, 소득, 거주지 상세 같은 민감 정보는 **묻지 않는다.** 복지 혜택의 자격 판정은 하지 않고 "대상은 기관 안내로 확인"이라고 쓴다.
- 추천 로직은 단순 태그 매칭(혜택의 `topics` 태그 ∩ 사용자 관심 분야, `wheelchair` 태그는 "휠체어 이용자 대상 또는 이동 관련" 항목 우선 표시)만 쓴다. 숨은 추론이나 프로파일링은 하지 않는다.
- 초기화·삭제 버튼을 "내 설정"에 둔다. 처음에는 선택 입력임을 안내한다.

### 6-2. 혜택 항목 데이터 모델 (제안)
`{ id, title, summary(원문 요약 1~2문장), topics[], wheelchairRelevant(true|false|null), area('북구'|'광주'|'전국'), period{start,end}|null, how(신청 방법 안내 링크), sourceName, sourceUrl, confirmedAt, license('공공누리4'|'제한없음'|...) , status('확인됨'|'확인 필요') }`
- `sourceUrl`·`confirmedAt`이 비면 앱에 노출하지 않는다.
- 종료일이 지난 항목은 자동으로 숨긴다. 갱신일이 오래된 항목에는 "마지막 확인일" 칩을 보인다.

### 6-3. 앱 안 위치
- **혜택알림 탭**(이미 존재: `src/pages/TabPages.tsx`의 `혜택알림` 페이지, 이번에 코드는 열람만): 관심 분야 선택 칩 + 맞춤 카드 목록 + "기준일·출처" 표시.
- **홈 소식**: 홈에 "이번 주 소식" 한 줄 카드 1~2개(마감 임박·북구 신규). 탭으로 연결.
- **지도 레이어 버튼**: 레이어 토글에 "상품권 가맹점"(부끄머니/상생카드/온누리 하위 토글)과 "휠체어 접근 정보 있는 가맹점" 필터. 기존 레이어(장애요소·정류장·화장실·새빛콜 승하차)와 같은 UI.
- 발표 시연용으로 "용봉동 상품권 가맹점 → 정보 있음/확인 필요" 비율을 한 화면에 보여 주면 데이터 공백(제보 필요성)이 근거로 드러난다.

## 7. 구현안 비교와 권장

용량은 가정 기반 추정이다(가맹점 1,000~2,000곳 × 약 250바이트).

| 안 | 내용 | 장점 | 단점 | 난이도 | 용봉동 데이터 규모 |

**권장: A로 시작하고, 발표 이후 필요하면 C로 확장.** 발표용 프로토타입이고 정적 웹 원칙(키 비노출)에 맞는다.

1. (확인, 호출 수 몇 번) 한국조폐공사 가맹점 API로 **북구 용봉동 `totalCount`와 부끄머니 포함 여부**를 확인한다. 이 결과로 공식 좌표 데이터 사용 여부가 정해진다. (키 활용신청 승인 여부 먼저 확인)

3. 가맹점 정규화 스크립트: 필드 최소화(가게명, 업종, 주소, 좌표, 상품권 종류, 기준일. 사업자등록번호·전화번호는 저장하지 않음), 용봉동 필터, 좌표 없으면 기존 지오코딩 캐시 방식으로 보강.
4. 편의시설 매칭(4-2 규칙) → 3단계 상태 부여 → 표본 20곳을 팀이 지도에서 눈으로 확인.
5. 지도 레이어 + 핀 상세(출처·기준일·3단계 칩) 구현.
6. 혜택 JSON: API 수집(복지서비스) + 북구 누리집 항목 **사람이 큐레이션**(제목·기간·링크만). 출처 URL·확인일 필수.
7. 혜택알림 탭 맞춤 필터(localStorage), 홈 소식 카드.
8. 발표 전 점검: 확인일 최신화, 마감 지난 항목 제거, "확인 필요" 문구 점검.

## 8. 사용자에게 확인할 것

1. "북구머니"는 **부끄머니(북구사랑상품권)**를 뜻하는 것이 맞는지.
2. 상품권 범위: 부끄머니 + 광주상생카드 + 온누리 세 가지를 모두 지도에 올릴지, 발표용으로 부끄머니 한 종류에 집중할지. (온누리는 용봉동 시장·상점가가 있는지부터 확인 필요)
3. 북구 민생경제과에 부끄머니 가맹점 파일·이용 허락을 문의해도 되는지(문안은 별도 작성 가능). 북구 누리집이 변경금지 조건이라 목록을 긁어 쓰는 방식은 피하는 것이 안전하다.
4. `DATA_GO_KR_KEY`로 한국조폐공사 가맹점 API 활용신청이 되어 있는지(없다면 팀 계정으로 신청 필요. 키 값은 보지 않고 승인 여부만 확인).
5. 혜택 목록은 "공식 출처가 있는 항목만 사람이 검수해 수십 건" 수준이면 충분한지, 아니면 복지서비스 API 전량을 넣을지.
6. 새빛콜(교통약자 이동지원센터)의 현행 요금·대상은 공식 최신 페이지를 팀이 직접 확인해 줄 수 있는지(이번에는 확인 안 됨).
7. 휠체어 이용 여부 선택 입력을 맞춤 화면에 넣어도 되는지(저장은 기기 안에서만, 서버 전송 없음).

## 10. 11/11 API 1회 확인 결과

- 사용자 허락(11/11)에 따라 전국지역화폐가맹점표준데이터 API를 기존 공공데이터 키로 **1회만** 호출했다(필터 없이 1페이지 1,000행 요청). 키 값은 출력·저장하지 않았고 임시 스크립트는 삭제했다. 응답 원본은 저장하지 않았다.
- 호출 주소: `https://api.data.go.kr/openapi/tn_pubr_public_local_bill_api` (데이터포털 카탈로그 JSON https://www.data.go.kr/catalog/15100062/openapi.json 의 contentUrl, 확인일 2026-11-11).
- 결과: HTTP 403, `SERVICE_KEY_IS_NOT_REGISTERED_ERROR`(등록되지 않은 서비스키, 코드 30). 즉 **이 API는 현재 키로 활용신청이 되어 있지 않다.** 재시도하지 않고 멈췄다.
- 따라서 ⓑ총 건수, ⓒ용봉동·북구 가맹점 수, ⓓ지역화폐명 값(부끄머니 포함 여부), ⓔ위경도 채움 비율은 **모두 확인 안 됨**이다.
- ⓕ필드명은 호출이 아니라 카탈로그 설명 기준(26개): 제공기관코드, 가맹점구분ID, 사업자등록번호, 가맹점등록구분, 가맹점명, 가맹점결제유형구분, 가맹점결제유형구분명, 가맹점대표전화번호, 사용처지역코드, 읍면동코드, 읍면동명, 가맹점우편번호, 가맹점주소, 가맹점상세주소, 위도, 경도, 표준산업분류코드, 표준산업분류코드명, QR등록상호명, 면세상품취급여부, 도서및공연취급여부, 온라인배달업체사용여부, POS사용여부, 지류가맹점신청여부, 사업자상태코드, 사업자상태코드명. 응답 필드의 영문 실제 이름·요청 변수 이름은 확인 안 됨. **지역화폐(상품권) 이름 필드는 목록에 없다**: 상품권 종류는 제공기관코드나 사용처지역코드로 가려야 할 수 있다(확인 안 됨).

## 11. 사용자 결정 반영 (11/11)

1. "북구머니"는 **사용자 기억 '북구머니' = 공식명 부끄머니로 판단**하고 진행한다.
2. 레이어 범위: 부끄머니·광주상생카드·온누리상품권 **세 가지 모두**.
3. API 1회 확인은 위 10절 결과(활용신청 필요)로 끝났다.
