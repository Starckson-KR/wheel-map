# 인터랙션 기획안 (이의있음!)

작성 11/18 · 읽기 조사만 했고 코드는 고치지 않았다. 청중은 앱 개발 경험이 없는 비전공 학부생·교수님, 시연은 휴대폰 화면(390×844).
방향: 화면이 "바뀌는 것"을 보여 주는 대신, 이용자가 **끌고·누르고·넘기고** 그 손길에 화면이 답하게 한다.
**이번 범위 밖**: 첫 화면 후킹 모션 팝업, 크리스마스 이스터에그(주말 마지막 단계). 그때 쓸 수 있는 공용 부품은 ★로 표시.

## 0. 먼저 알아 둘 것

**이미 있는 것(새로 만들지 않고 재사용)**
- `motion` 14.14.0이 이미 설치되어 있다(LazyMotion + domMax, `strict`라서 `m.*`만 쓴다). domMax에는 끌기(`drag`)와 `layoutId`가 들어 있다. **라이브러리 추가 없이 전부 가능.**
- `src/lib/motionTokens.ts`: `SPRING.screen/sheet/quick/press`(모두 거의 임계 감쇠), `FADE`, `TAP`, `PAGE_SHIFT`. CSS: `--ease-out`, `--ease-drawer`(tokens.css).
- `src/lib/sheetMotion.ts`(`springTo`·`releaseVelocity`·`resist`), `SheetHandle`·`useSheetSnap`(시트 끌기), `CountUp`, `SegBg`, `PressButton`, `RiseLi`, `prefersCalm()`.
- 탭 전환(좌우 18px 슬라이드 + 하단 탭 표시선 미끄러짐), 홈 타일 순차 등장, 칭호 진행 막대, 보상 토스트(`RewardToasts`)도 이미 있다.
- `ReportFlow`는 `initialType`을 받는다(유형 미리 고르기). 확인 투표는 `ReportDetail`의 「현장이 맞아요」(store `vote`).

**움직임 규칙(모든 후보 공통)**
- 기본은 켬. `html.motion-reduce`일 때: 이동·크기 변화는 즉시, 투명도만 바뀜. 색종이·튕김·진동은 끈다. `MotionConfig`는 `m.*`만 막으므로 **직접 짠 rAF·진동 코드는 `prefersCalm()`을 직접 확인**해야 한다.
- 모든 제스처에는 **한 번 누르기 대안**이 눈에 보이는 버튼으로 있어야 한다(끌기를 못 하는 사람이 대상). 큰 터치 영역(프로젝트 기준 44px 이상).
- 동행지도는 카카오 지도 위라 지도 끌기·두 손가락 확대와 겹치는 제스처는 쓰지 않는다. 지도에서는 "지도를 끄는 동작 그대로" 활용하는 것(C1)만 제안한다.

**조사 근거(확인한 것 / 못 한 것)**
- 확인함 — WCAG 2.2 SC 2.5.7 끌기 대안: 끌기에 의존하는 기능은 끌지 않고 한 번 누르기·클릭으로도 되어야 하고, 키보드만으로는 충족이 안 된다. https://www.w3.org/WAI/WCAG22/Understanding/dragging-movements.html
- 확인함 — SC 2.5.1 포인터 제스처: 두 손가락·경로(밀기) 제스처가 필요한 기능은 한 손가락 한 번 동작으로도 되어야 하고, 그 대안에 끌기를 쓸 수 없다(길게 누르기는 가능). https://www.w3.org/WAI/WCAG22/Understanding/pointer-gestures.html
- 확인함 — SC 2.3.3(AAA) 상호작용 움직임: 끌 수 있어야 하며, `prefers-reduced-motion` 존중이 충족 방법. 우리는 앱 설정 스위치로 같은 효과. https://www.w3.org/WAI/WCAG22/Understanding/animation-from-interactions.html
- 확인함 — SC 2.5.8 최소 터치 크기 24×24 CSS px(최소선). 우리는 그보다 크게(44px) 잡는다. https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html
- 확인함 — Apple HIG 제스처(JSON 원문): 사용자가 특정 제스처를 쓸 수 있다고 가정하지 말 것, 맞춤 제스처는 "꼭 필요할 때만, 발견하기 쉽게, 중요한 동작의 유일한 방법이 되지 않게", 시스템 UI 제스처와 충돌 금지, 길게 누르기는 "추가 기능 보이기" 용도. https://developer.apple.com/design/human-interface-guidelines/gestures
- 부분 확인 — 길게 누르기 시간: Android 기본 400ms(AOSP 커밋 기록, 공식 API 문서에 숫자는 직접 못 봄) https://developer.android.com/reference/android/view/ViewConfiguration , iOS UIKit 기본 0.5초(Apple 페이지에서 숫자 직접 확인은 못 함, 일반 지식). → 이 문서는 **450ms를 제안값**으로 쓴다.
- **못 확인** — Material 3 제스처 페이지는 본문이 읽히지 않았다. 당겨서 새로고침의 "정해진 기준 거리"도 공식 수치를 찾지 못했다. → 아래 72px는 **제안값이며 실기기에서 조정**한다.
- 부분 확인 — `navigator.vibrate`: MDN은 "제한적 지원"만 표시. iOS Safari 미지원·Chromium 계열은 화면을 한 번 만진 뒤에만 동작은 일반 지식(직접 확인 못 함). https://developer.mozilla.org/en-US/docs/Web/API/Vibration_API

## 1. 후보 18개

표기: 크기 S(반나절 안)·M(하루 안팎)·L(1~2일). 값(ms·px)은 제안값, 실기기에서 조정.

### 홈

**A1. 당겨서 새로고침**
- 화면·동작: 홈 맨 위에서 아래로 끈다.
- 반응: 손가락을 따라 72px까지 저항 0.5로 내려오고, 임계(72px)를 넘으면 아이콘이 돌며 「새 소식 확인 중」. 끝나면 `CountUp`이 0.6초 다시 올라가고 소식 카드가 `RiseLi`로 다시 순차 등장. 놓으면 `SPRING.screen`으로 복귀.
- 발표 효과: 누구나 아는 동작이라 따로 설명 없이 "앱 같다"가 바로 전달된다. 숫자가 다시 차오르는 순간이 볼거리.
- 대안·접근성: 소식 제목 옆 「새로고침」 버튼(한 번 누르기). 끄기 설정에서는 숫자만 즉시 갱신.
- 크기·파일: M — `HomePage.tsx`, `home.css`, 새 훅 `usePullRefresh`.
- 위험: 브라우저 기본 당겨서 새로고침과 겹침 → 홈 스크롤 영역에 `overscroll-behavior-y: contain` 필요(구현 때 현재 값 확인). 데이터는 기기 안에 있어 "새로고침"이 실제로 가져오는 건 없음 → 문구는 「새 소식 확인 중」보다 효과에 맞게(실제로 하는 일만: 계산 다시 하기).

**A2. 상황별 이동 가이드 넘기기**
- 화면·동작: 「버스 타기·길 건너기·건물 출입·신고 방법」 안내 카드를 좌우로 민다.
- 반응: 카드가 손가락을 1:1로 따라가고, 폭의 30% 또는 속도 500px/s를 넘으면 옆 카드로 `SPRING.sheet`로 안착. 위쪽 칩의 표시선(`SegBg`)이 같이 미끄러짐.
- 발표 효과: 가로 스와이프로 정보를 "넘겨 본다"는 직접 조작. 홈이 정적 목록이 아니게 된다.
- 대안·접근성: 기존 칩 4개를 그대로 눌러도 된다(칩이 대안). 스크린리더는 칩만 읽음.
- 크기·파일: M — `HomePage.tsx`(가이드 구역), `home.css`.
- 위험: 칩 줄 가로 스크롤과 제스처가 겹침 → 카드 영역에만 `touch-action: pan-y`. 세로 스크롤 중 비스듬한 끌기가 넘김으로 오인될 수 있어 방향 잠금(처음 8px 이동 방향)이 필요.

**A3. 오늘 장애요소 칩 → 지도로 날아가기**
- 화면·동작: 「지나기 어려움 N / 주의 N / 괜찮음 N」 칩 중 하나를 누른다.
- 반응: 누른 칩이 `TAP`으로 눌렸다 튀고(`SPRING.press`), 숫자가 한 번 커졌다 돌아온 뒤 해당 정도만 켜진 지도로 이동(`#/map` + 필터).
- 발표 효과: "숫자를 누르면 그 곳들이 지도에 나온다"가 한 동작으로 이해된다.
- 대안·접근성: 원래 누르기 동작이라 대안이 필요 없음. 기존 「지도 보기」 링크 유지.
- 크기·파일: S — `HomePage.tsx`, 지도 필터 진입 옵션(`lib/nav.ts`, `mapFilter.ts` 확인 필요).
- 위험: 지도 필터를 주소 옵션으로 받는지 확인 필요(받지 않으면 M).

**A4. AI 질문 칩 → 입력창으로 날아가 채움**
- 화면·동작: AI 검색의 추천 질문 칩을 누른다.
- 반응: 칩이 입력창 위치까지 0.35초 곡선(`--ease-drawer`)으로 날아가 글자가 채워지고, 결과 카드가 40ms 간격으로 올라옴(`RiseLi`).
- 발표 효과: 질문이 "입력되는 과정"이 보인다. 시연 때 타이핑 시간을 줄이는 실용 효과도 있음.
- 대안·접근성: 칩 누르기 자체가 대안. 움직임 줄이기에서는 즉시 채움.
- 크기·파일: S~M — `AiSearch.tsx`(이 문서에서는 구조만 확인, 칩 유무는 구현 때 확인).
- 위험: 날아가는 복제본 DOM이 포커스·스크린리더에 잡히지 않도록 `aria-hidden`.

### 하단 탭·화면 전환

**B1. [제보] 버튼 길게 눌러 유형 부채꼴 ★ 대표 "우와"**
- 화면·동작: 가운데 원형 [제보]를 450ms 누르고 있으면 위쪽으로 자주 쓰는 유형 5개(계단·턱 / 불법 주정차 / 파손 노면 / 쓰레기 / 더보기)가 부채꼴로 펼쳐진다. 손가락을 그대로 끌어 원하는 유형 위에서 놓으면 그 유형으로 제보 시작.
- 반응: 누르는 150ms부터 버튼 둘레에 링이 차오름(진행 표시) → 450ms에 버튼 크기 1.12배 + 진동 10ms + 유형 버튼이 30ms 간격·`SPRING.quick`로 퍼짐. 놓은 곳이 없으면 닫힘. 고른 유형 아이콘이 커지며 제보 화면으로(`initialType` 사용).
- 발표 효과: 한 손가락 동작 하나로 "유형 선택 + 제보 시작"이 끝나는 걸 보고 "어? 이렇게 되네"가 나오는 장면. 휠체어 이용자가 한 손으로 쓰기에도 맞는 설명이 된다.
- 대안·접근성: **짧게 누르기 = 기존대로 제보 화면**(유형 12개 목록). 즉 길게 누르기는 지름길일 뿐 필수가 아님(HIG: 중요한 동작의 유일한 방법이 아니게). 스크린리더 사용자는 「제보하기」 버튼의 사용자 정의 동작 대신 기존 화면. 유형 버튼은 44px 이상, 아이콘+글자 함께.
- 크기·파일: M~L — `TabBar.tsx`, `home.css`(탭바 스타일 86줄 근처), 새 `useLongPress`, `ReportTypeIcon.tsx` 재사용, `lib/reportTypes.ts`(12유형 중 5개 선정은 사용자 결정 후보).
- 위험: iOS 길게 누르기 기본 동작(글자 선택·돋보기·메뉴) → `-webkit-touch-callout: none; user-select: none; touch-action: none`을 [제보] 버튼에만. 화면 아래 가장자리에서 끌어 올리는 동작은 iOS 홈 표시줄 위로 쓸기와 비슷해 오작동 가능 → 부채꼴은 버튼보다 위쪽 화면 안쪽으로만 펼치고, 끌기 판정은 버튼 중심에서 반경 기준. 놓은 곳이 유형이 아니면 취소(실수 접수 방지: 놓은 다음에도 제보 화면 1단계에서 취소 가능).

**B2. 제보 버튼에서 화면이 원형으로 퍼지는 전환**
- 화면·동작: [제보]를 짧게 누른다(또는 B1의 놓기).
- 반응: 새 화면이 [제보] 버튼 중심에서 원형(`clip-path: circle()`)으로 0.38초 `--ease-drawer`로 퍼진다. 기존 좌우 슬라이드(탭 전환)는 그대로 두고 이 한 번만 다르게.
- 발표 효과: 가운데 버튼이 "눌러서 새로 여는 것"임을 몸으로 이해. 화면 전환 시연 요구에 해당.
- 대안·접근성: 움직임 줄이기에서는 투명도만. 누르기 동작 자체는 같음.
- 크기·파일: M — `App.tsx`(페이지 전환 부분), `TabBar.tsx`, 시작 좌표 전달.
- 위험: `clip-path`는 그리기 비용이 있어 휴대폰에서 0.4초 동안 끊길 수 있음 → 실기기 확인, 안 되면 `scale`+투명도로 대체. 동행지도는 유지되어 숨기기만 하는 구조(`app-keep`)라 지도 위에서 시작할 때 별도 확인 필요.

**B3. 탭 아이콘 작은 반응**
- 화면·동작: 하단 탭을 누른다.
- 반응: 아이콘이 0.25초 안에 한 번 튄다(홈=문 열림, 혜택알림=종 흔들림, 내 정보=머리 끄덕). 표시선은 이미 미끄러짐.
- 발표 효과: 작지만 "모든 곳이 살아 있다"는 인상. 비용 대비 가장 싸다.
- 대안·접근성: 장식이므로 대안 불필요, `aria-hidden`.
- 크기·파일: S — `TabBar.tsx`, `Icon.tsx` 일부, CSS 키프레임.
- 위험: 거의 없음(아이콘 transform만). 효과가 과하면 산만 → 한 번만 재생.

### 제보하기

**C1. 지도를 끌면 중앙 핀이 들려 올라가는 위치 고르기**
- 화면·동작: 위치 고르기에서 화면 중앙에 핀이 고정되어 있고, 이용자는 **지도를 끌어** 핀 아래 위치를 맞춘다.
- 반응: 끌기 시작 시 핀이 12px 위로 떠오르고 그림자가 작고 흐려짐(120ms), 놓으면 `SPRING`(오버슈트 허용)으로 통 하고 내려와 그림자가 커짐. 아래에 "○○동 ○○ 부근" 주소가 갱신.
- 발표 효과: "핀을 직접 들어서 놓는" 느낌인데 실제로는 지도 끌기라서 충돌이 없다. 지도 앱을 아는 사람이면 바로 이해.
- 대안·접근성: 「내 위치로」 버튼, 주소 검색, 한 번 누르면 그 위치로 지도 이동(현재 탭으로 고르는 방식과 같은 입력). 핀 이동은 장식이라 대안 문제 없음.
- 크기·파일: M — `BarrierMap.tsx`(`picking`·`draftPos` 근처, 카카오 `dragstart`/`dragend`/`center_changed`), `ReportFlow.tsx`, `map.css`.
- 위험: 지금은 "지도를 한 번 누르면 그 자리"인 방식이라 바꾸는 범위가 큼(기존 방식도 남기기). `center_changed`는 자주 불려 주소 조회는 `dragend` 후에만(성능). 핀을 직접 끌어 옮기는 방식은 지도 끌기와 충돌하므로 **채택하지 않는다**.

**C2. 유형 카드 선택 반응**
- 화면·동작: 12유형 카드 중 하나를 누른다.
- 반응: 아이콘이 1→1.25→1로 튀고(`SPRING.quick`, 오버슈트 허용) 카드 테두리가 0.18초에 선택색으로, 진동 8ms.
- 발표 효과: 첫 단계부터 "눌렀다"는 확실한 피드백. 작업량 대비 체감 큼.
- 대안·접근성: 누르기 그 자체. 선택은 색만이 아니라 체크 표시도 함께(기존 규칙 유지).
- 크기·파일: S — `ReportFlow.tsx`(유형 단계), `ReportTypeIcon.tsx`, `flows.css`.
- 위험: 없음.

**C3. 줄자 끌기: 보도 폭·턱 높이 맞추기**
- 화면·동작: 측정(폭 m·턱 cm)을 숫자 입력 대신 줄자 막대를 끌어서 맞춘다.
- 반응: 막대 위에 판정 선(폭: 1.2m 미만=어려움, 1.2~2m=주의, 2m 이상=괜찮음. 이미 `ReportDetail`의 ○△X 기준에 있는 값)이 있고, 끌 때 막대 색이 선을 지나며 0.12초에 바뀐다. 선을 지나는 순간 진동 8ms. 한 눈에 "이 보도는 휠체어가 지나기 어렵다"가 보임.
- 발표 효과: 청중이 "휠체어 기준으로 어렵다/괜찮다"의 감을 직접 만진다. 정책 발표 주제와 맞아 **설명이 곧 시연**.
- 대안·접근성: 숫자 입력칸을 막대 아래 항상 둔다(눌러 직접 입력, 키보드 가능). 막대는 `role="slider"` + 방향키 0.1m씩.
- 크기·파일: M — `ReportFlow.tsx`(측정 입력 3단계), 새 `RulerSlider.tsx`, `flows.css`.
- 위험: 시민이 적은 값이라 오차가 있다는 기존 문구 유지. 수치 기준은 이미 화면에 있는 판정 기준만 사용하고 새 기준을 만들지 않는다(명세 13장 4번: 확인 안 된 값은 "확인 필요").

**C4. 길게 눌러 접수**
- 화면·동작: 4단계 맨 아래 「접수하기」를 누르고 있는다.
- 반응: 누르는 동안 버튼이 왼쪽에서 오른쪽으로 700ms에 걸쳐 채워지고(진행 링), 다 차면 접수. 중간에 떼면 0.2초에 되돌아가며 「조금 더 누르세요」.
- 발표 효과: 잘못 눌러 접수되는 일을 막는 설계를 눈으로 보여 줄 수 있다("실수 방지"가 설명 포인트).
- 대안·접근성: **일반 누르기도 접수된다**(Enter·Space·스크린리더 활성화는 즉시 접수). 터치에서는 "짧게 눌러 한 번 더 누르면 접수" 2단 확인 방식을 대안으로 두거나, 사용자가 정한 기본값(§4)에 따른다. 손 떨림·근력 약한 이용자 때문에 **길게 누르기만 있는 상태는 금지**.
- 크기·파일: S~M — `ReportFlow.tsx`(제출 버튼), 새 `useLongPress`(B1과 공유).
- 위험: 의미 없이 번거로워 보일 수 있음. 접수는 가벼운 행위라 필수는 아님 → 효과 대비 B1이 우선.

**C5. 접수 완료 축하 ★**
- 화면·동작: 접수가 끝나는 순간(자동).
- 반응: 체크 원이 0.4초에 그려지고(경로 그리기), 접수 번호가 도장처럼 1.3배→1로 `쾅`(오버슈트 허용, 220ms), 색종이 24조각이 0.9~1.2초에 걸쳐 올라갔다 떨어짐, 진동 `[12, 40, 12]`ms. 이어서 3단계 안내(`다른 시민 확인 → 기관 접수 → 처리 결과`)가 90ms 간격으로 순서대로 켜짐.
- 발표 효과: 시연의 "마무리 장면"이 정적 문구에서 축하 장면으로. 청중이 박수 칠 지점.
- 대안·접근성: 읽기 쉬운 문구와 접수 번호는 기존 그대로(색종이는 `aria-hidden`). 움직임 줄이기: 색종이 없음, 체크는 투명도만.
- 크기·파일: M — `ReportFlow.tsx`(완료 화면), `flows.css`, **공용 `Celebration` ★**.
- 위험: 색종이 DOM이 많으면 느림 → 24~32개, `transform`·`opacity`만, 끝나면 DOM 제거.

### 확인(검증)·재확인

**D1. 확인 투표 카드 넘기기 ★ 가장 "직접 참여"**
- 화면·동작: 「확인할 제보」 카드 스택. 오른쪽으로 밀면 「현장이 맞아요」(투표), 왼쪽으로 밀면 「넘기기」(투표하지 않고 다음 카드).
- 반응: 카드가 손가락을 따라 기울며(±12° 이내) 움직이고, 폭의 35%를 넘으면 오른쪽에 초록 「맞아요」 도장이 점점 진해지다가 놓으면 카드가 날아가고 다음 카드가 `SPRING.screen`으로 올라온다. 투표가 되면 점수 토스트가 같이 나온다. 3초간 「되돌리기」.
- 발표 효과: 데이팅 앱식 스와이프로 "이웃의 제보를 내가 확인한다"는 참여 구조를 몸으로 보여 준다. 시연 이름: 지도에 올라가기 전 단계(검증)를 청중이 직접 해 본다.
- 대안·접근성: 카드 아래에 항상 「현장이 맞아요」「넘기기」 두 버튼(44px 이상). 기존 `ReportDetail`의 버튼도 유지. 사진·위치를 보지 않고 넘기는 습관을 막기 위해 카드에는 사진 한 장과 위치를 먼저 보이고, 제보 내용을 펼쳐 본 뒤 버튼이 활성화되는 방식도 가능(사용자 결정 여지).
- 크기·파일: L — `TabPages.tsx`(`ReportTab`에 구역 추가) 또는 새 `VerifyDeck.tsx`, `reportStore.ts`의 `vote` 재사용, `review.css`.
- 위험: 잘못 밀어 허위 확인(점수 연결) → 되돌리기 3초와 확인 팝업 없는 대신 "되돌리기"로 해결. 확인할 제보가 0건이면 빈 화면 → 시연 데이터에 대기 제보가 있는지 사전 확인 필요(인수인계: 재확인 대기 약 99건, 검증 대기는 확인 필요). 스와이프 방향 판정(세로 스크롤과 구분)은 A2와 같은 방향 잠금을 공유.

**D2. 조치 전·후 사진 비교 슬라이더**
- 화면·동작: 개선 현황/재확인 화면의 전·후 사진을 가운데 선을 좌우로 끌어 비교한다.
- 반응: 선이 손가락을 따라 움직이며 위 사진이 `clip-path: inset()`으로 열림. 놓으면 가까운 쪽 끝이 아니라 그 자리에 머문다. 처음 보일 때 한 번 좌→우→중앙으로 0.8초 자동 시범.
- 발표 효과: "고쳐졌다"를 설명하지 않고 보여 줌. 사진이 크게 바뀌는 장면은 청중이 가장 이해하기 쉽다.
- 대안·접근성: 가운데 선 아래 「전 / 후」 토글 버튼(누르면 사진 전환). 선은 `role="slider"` + 방향키. 사진에는 대체 문구.
- 크기·파일: M — `BeforeAfter.tsx`(23줄, 지금은 나란히 보이기), `ProgressPanel.tsx`.
- 위험: 시연 데이터에 실제 전후 사진이 없음(인수인계: "사진이 나란히 뜨는 화면은 미확인") → `samplePhotos.ts`로 시연용 쌍을 만들어야 함(가상 표시 필수, 실제 현장 사진으로 오인되지 않게). 긴 사진은 `clip-path` 갱신이 무거울 수 있어 이미지 크기 제한.

### 내 정보·혜택알림

**E1. 칭호 승급 연출 ★**
- 화면·동작: 새 칭호·엠블럼을 받는 순간(자동), 기존 `RewardToasts`의 한 줄 알림 대신 승급 장면.
- 반응: 화면이 0.2초 어두워지고, 엠블럼이 0.6→1.0배로 오버슈트 12%(280ms)로 나타나며 뒤에서 빛이 한 바퀴 돎. 「길 지킴이 칭호를 받았어요」 + `Celebration` + 진동. 아무 곳이나 누르면 닫힘(3.5초 후 자동으로 토스트로 줄어듦).
- 발표 효과: 게임식 보상이 정책 서비스의 "참여 동기"임을 한눈에. 교수님께 "참여를 지속시키는 장치"로 설명하기 좋음.
- 대안·접근성: 같은 내용을 `role="status"` 문구로 읽어 준다. 닫기 버튼 44px. 움직임 줄이기: 빛·색종이 없이 엠블럼 투명도만, 토스트로 대체 가능.
- 크기·파일: M — `RewardToasts.tsx`(`diffRewards` 결과의 새 엠블럼 분기), 새 `RewardCelebrate.tsx`, `rewards.css`, `RewardEmblem.tsx`.
- 위험: 시연 중 갑자기 막으면 흐름이 끊김 → 크게 칭호 받을 때만(작은 점수는 토스트 유지, 현 규칙과 같음). 여러 명 칭호가 한꺼번에 오르면(시연 데이터 채우기) 이미 `bulk` 예외가 있어 같은 규칙 사용.

**E2. 점수 링 + 엠블럼 돌려 보기**
- 화면·동작: 내 기여 위쪽 큰 엠블럼 둘레에 다음 칭호까지 링이 있다. 엠블럼을 끌면 3D처럼 기울어지고, 누르면 뒤집혀 「획득 방법」이 나온다.
- 반응: 링은 0→현재값을 0.8초(`--ease-out`)에 채움(숫자 `CountUp`과 동기). 끌기: 최대 ±18° 기울기, 놓으면 `SPRING.screen`으로 복귀. 뒤집기: 0.35초.
- 발표 효과: 엠블럼이 "내 것"처럼 느껴지는 직접 조작. 이미지 시안이 나오면(7.5단계) 효과가 더 큼.
- 대안·접근성: 뒤집기는 엠블럼을 누르는 것이라 대안 불필요(기울기는 장식). 「획득 방법」은 화면 문구에 이미 있어 정보 손실 없음.
- 크기·파일: M — `MyRewards.tsx`(`rw-hero`), `RewardEmblem.tsx`, `rewards.css`, 홈 칭호 카드(`HomePage.tsx`의 `hp-me`)에도 같은 링 적용 가능.
- 위험: 3D 변형이 흐릿해 보일 수 있음 → `transform`만 쓰고 `backface-visibility`는 실기기 확인. 현재 엠블럼은 이모지+CSS라 큰 크기에서 평범해 보일 수 있음(시안 확정 전이라 효과 제한).

**E3. 랭킹 막대 차오름 + 내 순위로 이동**
- 화면·동작: 랭킹 탭을 연다.
- 반응: 행이 40ms 간격으로 올라오며 점수 막대가 0.6초에 차오르고, 내가 10위 밖이면 「내 순위 보기」 버튼이 나타나 누르면 내 행까지 부드럽게 스크롤하고 한 번 강조(배경색 0.8초).
- 발표 효과: 데이터 화면이 "움직이는 순위표"가 된다(경쟁·참여 포인트).
- 대안·접근성: 막대는 장식, 숫자·순위는 글자로 유지. 움직임 줄이기: 즉시 표시.
- 크기·파일: S~M — `ParticipationRanking.tsx`(이 문서에서는 구조만 확인), `rewards.css`.
- 위험: 이미 `RiseLi`가 있는지·행 수가 많은지 구현 때 확인. 낮음.

**E4. 알림 밀어서 읽음**
- 화면·동작: 알림 행을 왼쪽으로 밀어 「읽음」.
- 반응: 행이 손가락을 따라가며 뒤에서 「읽음」 라벨이 드러나고, 임계 넘으면 행 높이가 0.2초에 접힌다.
- 발표 효과: 메시지 앱 같은 익숙한 동작. 다만 알림이 기록에서 계산되는 파생 데이터라 읽음 상태 저장소가 새로 필요(효과 대비 비용이 큼).
- 대안·접근성: 행 끝에 「읽음」 버튼을 항상 둔다.
- 크기·파일: M — `TabPages.tsx`(`AlertsTab`), 새 저장 키(`wheelmap.*`).
- 위험: 읽음을 저장하지 않으면 새로고침 때 되돌아와 어색함. **하위 우선순위.**

나머지(A2·A3·A4·C4·E2·E3·E4)는 11위 이하. 가이드 넘기기(A2)·점수 링(E2)은 시간이 남을 때 추천, 알림 밀어서 읽음(E4)은 보류.

**시연 대본에서 보여 줄 순간(제안 순서)**
1. 홈: 아래로 당겨 숫자가 다시 차오름 (A1) → 한 줄 "오늘 장애요소 N곳".
2. [제보]를 길게 눌러 유형이 부채꼴로 펼쳐지고 "계단·턱"으로 끌어 놓음 (B1, 원형 확장 B2).
3. 지도를 끌어 핀을 맞춤, 핀이 통 하고 내려앉음 (C1) → 줄자로 보도 폭을 끌어 "어려움" 색으로 바뀜 (C3).
4. 접수 → 체크·도장·색종이 (C5).
5. 다른 시민 계정으로 확인할 제보 카드를 오른쪽으로 넘김 (D1).
6. 내 정보: 칭호 승급 장면 (E1).
7. 마지막: 조치 전·후 슬라이더로 "고쳐졌습니다" (D2).

권장 구현 순서: 공용 부품(§3) → C5 → B1 → C1 → D1 → E1 → D2 → A1 → C3 → B2 → 나머지. 단계마다 휴대폰 폭에서 눌러 확인하고, 움직임 줄이기 켠 상태에서 한 번씩 더 확인.

## 3. 공용 부품·라이브러리

**라이브러리: 추가 없음.** `motion` 14(domMax)가 끌기·`layoutId`·스프링을 이미 제공한다. 색종이는 직접 짠 DOM(24~32개, `transform`·`opacity`만)으로 충분해서 `canvas-confetti` 같은 패키지를 넣지 않는다.

| 부품 | 내용 | 쓰는 후보 |
|---|---|---|
| ★ `Celebration` | 색종이 24~32조각, 0.9~1.2초, 브랜드 색 4가지, 끝나면 DOM 제거. 움직임 줄이기에서는 그리지 않음. 위치(원점)를 받음 | C5, E1, (주말: 이스터에그·후킹) |
| ★ `haptic(kind)` | `tick` 8ms, `success` [12,40,12], `warn` [20]. `navigator.vibrate`가 없거나 움직임 줄이기 켜짐이면 아무 것도 안 함. 화면을 한 번 만진 뒤에만 동작하는 브라우저가 있어 첫 접촉 이후 호출 | B1, C2, C3, C5, D1, E1 |
| `useLongPress(ms=450, onFire, onProgress)` | 포인터 눌림 시간 측정, 150ms부터 진행값 전달, 10px 이상 움직이면 취소(스크롤과 구분), `touch-callout` 방지 | B1, C4 |
| `useDragCommit` | 가로 끌기 방향 잠금(처음 8px), 임계(폭 35% 또는 500px/s), `sheetMotion.springTo` 재사용 | A2, D1, E4 |
| `SPRING.pop` 추가 | `stiffness 700, damping 28`(오버슈트 약 15%). **지금 스프링은 모두 거의 임계 감쇠**라 튀는 느낌이 없으니, 축하·도장·유형 선택에만 허용 | C2, C5, E1 |
| 공용 값 | `LONG_PRESS_MS = 450`, `REFRESH_PULL = 72`, `COMMIT_RATIO = 0.35` → `motionTokens.ts`에 모아 한 곳에서만 고친다 | 전부 |
| easing | 새로 만들지 않고 기존 `--ease-out`(나타남)·`--ease-drawer`(시트·큰 이동) 사용. 닫힘은 0.12초(`FADE_OUT`) | 전부 |

**진동 지원 범위**: MDN은 "제한적 지원"만 표시(직접 확인). 일반적으로 Android Chrome 계열은 지원, **iOS Safari는 미지원**으로 알려져 있어 아이폰으로 시연하면 진동은 없다(직접 확인 못 함 → 시연 기기에서 실제로 확인). 진동은 항상 **보조**이고 같은 정보를 시각 반응으로도 준다.

**접근성 공통 체크(구현 후 각 후보에 적용)**: 눌러서 되는지 / 키보드로 되는지 / 스크린리더 이름 / 터치 영역 44px 이상 / 움직임 줄이기에서 정보가 남는지 / 끌기 중 세로 스크롤이 막히지 않는지.

## 4. 사용자가 정할 것 (3개)

1. **시연 휴대폰이 아이폰인가요, 안드로이드인가요?** 아이폰이면 진동이 나지 않으므로 진동은 "있으면 좋은 것"으로만 두고, 소리·시각 반응에 힘을 둡니다. 어느 쪽인지에 따라 B1·C5의 마무리 연출이 달라집니다.
2. **D1(확인 투표 카드 넘기기, 규모 L)을 이번에 넣을까요?** 가장 참여감이 크지만 신규 화면이라 시간이 큽니다. 안 넣으면 순위 4~6번(C1·E1·D2)을 앞당깁니다. 넣을 경우 사진·위치를 먼저 보여 준 뒤 버튼이 켜지게 할지도 함께 정해 주세요.
3. **부채꼴(B1)에 어떤 유형 5개를 둘까요?** 12유형 중 시연과 현장에서 자주 쓸 것을 정해 주세요(제안: 계단·턱, 불법 주정차, 파손 노면, 쓰레기, 더보기). 그리고 접수(C4)는 길게 누르기를 기본으로 할지, 일반 누르기를 기본으로 하고 길게 누르기는 생략할지 정해 주세요(제안: 일반 누르기 기본, 길게 누르기는 생략).
